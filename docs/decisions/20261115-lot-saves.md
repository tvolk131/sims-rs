# A lot is saved as the state its next step depends on, and restored into a lot loaded from the same house

*Decided 2026-11-15.*

`sims_vm::boot::Lot::save` gives a `Saved`: the world, plus the lot's state
outside it. That state is:

- the ticks run since the load, which the frames schedule follows;
- the tick count the load left;
- the answers still to give;
- play mode's objects reset this tick;
- the house view's rotation, which Generic Sims Call 12 reads;
- whether a dialog was answered and the tick that showed it has not run
  again, during which the lot takes no input;
- the house and family the load selected, and the world's hash as the
  load left it.

This is the set a step that may ask the player already sets aside before
its tick, plus the parts the load fixes. `Lot::restore` puts it back into
a lot loaded from the same install and house. It refuses a save of another
house or family. It also refuses one whose loaded world's hash differs,
such as another neighborhood's house of the same number. It forgets any
dialog the lot waited on or any failed step. No test covers the hash
refusal, since the test install has one neighborhood.

The linked program, the catalog and the motive tuning are not saved:
loading the same house rebuilds them. The frames schedule and whether the
lot waits for answers are inputs given at load, as they are for any run.

A save taken while a dialog waits holds the world as it was before the
tick that showed the dialog, so the restored lot runs that tick again and
asks again. A save taken after the answer, before that tick runs again,
keeps the answer and refuses input until the next step, as the saved lot
does. A halted lot is refused, because its world is partway through
a step.

## The save format

A save is a new persistent format: it outlives the program that wrote it.
`Saved::encode` gives these bytes, in order:

1. `sims_vm::boot::save::FORMAT`, a little-endian u32. It is 1 now.
2. `sims_sim::SNAPSHOT_FORMAT`, the world's encoding version, a
   little-endian u32. It is 28 now.
3. The `Saved` struct, encoded with postcard.

`Saved::decode` refuses a save unless both numbers equal the reader's. It
never guesses at a save it might misread.

**What `FORMAT` covers.** It covers the lot's own fields in `Saved`: which
fields there are, their order and their types. Postcard is not
self-describing, so any change to `Saved` changes the layout. That
includes adding, removing, reordering or retyping a field, or changing a
type a field holds, such as `Answers` or `Play`'s set. Each such change
bumps `FORMAT` by one in the same commit.

**What `FORMAT` does not cover.** It does not cover the world inside a
save. The world's encoding is versioned by `SNAPSHOT_FORMAT`, which
sims-sim already bumps whenever `World`'s encoding changes. A save records
both numbers, so a change to either one refuses older saves.

**No migration.** An older save is refused, not migrated. Nothing reads an
older layout while the simulation is still changing.

**Tied to how the house loaded.** A save also carries the world's hash as
the load left it. So a change to what loading a house produces makes
older saves of that house refuse with `SaveError::OtherLoad`, even when
neither number changed. Such a change could be a fix to the load or a
new snapshot field. This is deliberate: a save is only known to step
correctly when it goes back onto the load it came from.

**The store.** `sims_sim::Snapshots` keeps saves as these bytes, by name,
in a `lots` table of the same REDB file as the world snapshots. sims-sim
does not need to know the lot's types. The table holds bytes only, so it
needs no version of its own.

## Tests

The tests on the Goth house check three things. A lot saved at update 500,
restored into a fresh load and stepped to 1000 matches the saved lot's
hash at every update. A lot saved while the Help System dialog waits asks
again at update 2 and then matches a lot answered at load. A lot saved
once that dialog is answered, before its tick runs again, refuses input
as the saved lot does and then matches it.

This is not the original's save. The original writes the house file and
the neighborhood, which is not ported, so a save here cannot be opened by
the original and the reverse also does not work.
