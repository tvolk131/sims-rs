# A lot is saved as the state its next step depends on, and restored into a lot loaded from the same house

*Decided 2026-11-15.*

`sims_vm::boot::Lot::save` gives a `Saved`: the world, plus the lot's state
outside it. That state is:

- the ticks run since the load, which the frames schedule follows;
- the tick count the load left;
- the answers still to give;
- play mode's objects reset this tick;
- the house view's rotation, which Generic Sims Call 12 reads;
- the house and family the load selected.

This is the set a step that may ask the player already sets aside before
its tick, plus the parts the load fixes. `Lot::restore` puts it back into
a lot loaded from the same install and house. It refuses a save of another
house or family, and it forgets any dialog the lot waited on or any failed
step.

The linked program, the catalog and the motive tuning are not saved:
loading the same house rebuilds them. The frames schedule and whether the
lot waits for answers are inputs given at load, as they are for any run.

A save taken while a dialog waits holds the world as it was before the
tick that showed the dialog, so the restored lot runs that tick again and
asks again. A halted lot is refused, because its world is partway through
a step.

`Saved::encode` writes its own layout version and the world's snapshot
format, then postcard. A save of another version is refused rather than
misread. `sims_sim::Snapshots` keeps saves in a `lots` table of the same
REDB file as the snapshots, by name, as bytes, so sims-sim need not know
the lot's types.

The tests on the Goth house check two things. A lot saved at update 500,
restored into a fresh load and stepped to 1000 matches the saved lot's
hash at every update. A lot saved while the Help System dialog waits asks
again at update 2 and then matches a lot answered at load.

This is not the original's save. The original writes the house file and
the neighborhood, which is not ported, so a save here cannot be opened by
the original and the reverse also does not work.
